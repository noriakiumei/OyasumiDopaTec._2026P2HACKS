# 006: 手続きを減らし、確認を強める

- 日付：2026-11-26
- 決めた人：（PR のレビューで決める。提案はいうてぃー）
- 変更：2026-11-26 相談の中身を書く場所を、ドライブから「要相談」の Issue・PR に変えた（理由は 007）

## 決めたこと

- AI は PR を出す前に実際に動かし、Issue の完了条件を1つずつ確かめる。確かめられなかったことは PR に書き、確かめていないことを「動いた」と書かない。
- Issue は「優先」ラベルが付いたものから取る。「優先」を付けるのは人。依存が終わっていない Issue は飛ばす。
- ブランチはすぐ push し、最初のコミットで下書きの PR を作る。同じ番号のブランチ・PR がある Issue には手を出さない。
- 作業が止まったら推測で進めず、Issue に理由と再開できる条件を書いて別の Issue に進む。
- 人に聞くのは、体験が大きく変わるときに絞る。小さくて戻せるものは作って見せる。小さな質問は PR・Issue のコメントで聞き、複数人で決めたいことや理由を残したい判断は「要相談」の Issue か PR に書く。
- ドライブにレビュー用ドキュメントを作るのは、大きな画面変更・音や動画・複数人で決めたいときだけにする。
- Issue の範囲外は触らない。気づいた改善は、小さな整理なら「整理：」の PR（Issue なしでよい）、それより大きいものは別の Issue にする。消す・まとめる前に動かして確かめる。
- 人に試してもらうためのビルドやデモ用データに、APIキー・個人情報・本番のデータを入れない。

## 理由

- AI は速く書けるので、質を決めるのは「本当に動くか」の確認になる。動かしていない PR が混ざると、人の確認の手間が増える。
- 優先の決まりがないと、AI が簡単な Issue から片づけ、体験の中心になる機能が後回しになる。
- 余白や色まで人に聞くと待ち時間が増える。実物を見て判断するほうが速い。
- 小さな変更のたびにドキュメントを作ると、管理が仕事になる。PR に試し方が書いてあれば足りる。
- 1人が同じアカウントで AI を複数動かすと、担当者だけでは重複に気づけない。ブランチと下書き PR があれば早く気づける。

## 検討したほかの案

- 優先度を P0〜P3 の4段階にする：付ける手間が増える。「優先」かどうかの2段階で足りる。
- AI のセッションごとに識別情報を Issue に書く：手続きが増える。ブランチと下書き PR で代わりになる。
- AGENTS.md を複数ファイルに分ける：今の長さなら1ファイルのほうが見つけやすい。

## 影響（変わること・注意すること）

- 「優先」ラベルを作る必要がある（`gh label create 優先`）。
- 試してもらう仕組み（Web なら自動デプロイ）、感想を拾う仕組み（Discord など）は、ルールを書いただけでは動かない。作るものの形と技術が決まったら最初の Issue にする。
