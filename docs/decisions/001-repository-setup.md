## 決めたこと

- リポジトリ `noriakiumei/OyasumiDopaTec._2026P2HACKS` は公開（public）にする。
- `main` ブランチを保護する。
  - マージには PR が必要（`main` に直接 push しない）。ほかの人の承認は要らない。PR を出した人が自分で読み、実際に動かしてからマージする。
  - 画面や操作感など、ほかの人に見てほしい変更は、PR の「レビューしてほしいところ」に書き、感想をもらってからマージする。
  - force push とブランチの削除は禁止。
  - 管理者（noriakiumei）は保護の対象外（`enforce_admins: false`）。
- 開発タスクは GitHub Projects のボード「OyasumiDopaTec. 2026P2HACKS」（https://github.com/users/noriakiumei/projects/1 、公開）で管理する。Status は「未着手・進行中・完了」。
- Issue のラベルは「機能」「不具合」「要相談」「ドキュメント」「優先」を使う。「優先」は人が付け、AI はこれが付いた Issue から取る。

## 理由

- 公開：P2HACKS2025 のチームリポジトリも公開されていた。コンテストで成果物を見せる前提に合わせた。
- main の保護：AI が書いたコードも含めて、必ず人が1人は読んでから main に入れるため（「チームの方向性」で、設計と最終判断は人が持つと決めた）。
- 承認を必須にしない理由（#10）：AI が速く PR を出すので、承認待ちがいちばん長い待ち時間になる。ひとりで進める時間帯は承認する人がいなくて止まる。PR を出した本人が読んで動かしてからマージすれば、「人が1人は読む」目的は守れる。
- 管理者を対象外にした理由：メンバーがそろう前でも、詰まったときに管理者がマージできるようにするため。普段は管理者も PR を通す。
- Projects：Google ドライブ（考える）と分けて、開発タスクの進み具合を GitHub 側で見るため。

## 検討したほかの案

- 非公開リポジトリ：招待リンクや秘密情報の漏れは防ぎやすいが、発表で見せるときに公開し直す手間がかかる。秘密情報は CLAUDE.md の禁止事項で防ぐことにした。
- 承認2人：5人のチームで本番中にレビュー待ちが増えるため、1人にした。
- ほかの1人の承認を必須にする（最初の設定）：待ち時間が長くなるため、#10 でやめた。
- ルール（`AGENTS.md`・`docs/decisions/`・`.github/`）を変える PR だけ承認を必須にする（CODEOWNERS を使う）：設定が思ったとおり動くか確かめていないため、見送った。
