# 009: 人の確認が要るときは、Discord のボットで本人に直接知らせる（MCP サーバー）

- 日付：2026-11-26（2026-11-27 にネット上に置く形へ変更、Issue ごとのスレッドを追加）
- 決めた人：（PR のレビューで決める。提案はいうてぃー）

## 決めたこと

- AI が人の確認を必要としたとき（マージ前のレビュー、「要相談」の判断）、Discord でその人をメンションしてレビュー依頼を送り、その件のスレッドを開く。返信は AI が読む。
- ボットは MCP サーバーとして出し、Cloudflare Workers（無料枠）に1つだけ置く（`tools/review-bot/worker.mjs`）。メンバーは鍵入りの URL を自分のエージェントに1回登録するだけで使える。依存パッケージなし。
- ボットのトークンと、GitHub のログイン名と Discord のユーザー ID の対応表は、Worker の設定（Variables and Secrets）にだけ置く。リポジトリは public なので、アカウントの対応も鍵入りの URL も載せない。URL はオンボーディング資料に書く。
- 手元で動かす版（`server.mjs`、stdio）は開発・確認用に残す。
- Issue ができたら、GitHub Actions がボットを呼んで Issue ごとのスレッドを立てる（メンションなし）。PR は本文の `Closes #番号` でそのスレッドにつなぎ、レビュー依頼もそのスレッドで出す。Issue の無い PR だけ PR 用のスレッドを立てる（#19、chico の提案と選択）。
- チームTast の Uni ボットは使わない（Uni はチームTast 専用）。

## 理由

- みんなが普段見ている Discord に本人宛てで届くので、レビュー待ちの時間がいちばん縮む。感想もその件のスレッドにまとまる。
- MCP の道具にすれば、Claude でも Codex でも同じように使える。AGENTS.md には「人の確認が要るときは本人に直接届く形で知らせる」という目的だけを書き、道具の名前は例として添える。
- 最初は各自が手元で起動する形にしたが、`.env`（トークン入り）を全員に配るのが手間で、漏れる場所も増える。ネット上に1つ置けば、配るのは URL だけで、トークンはメンバーの手元に出ない（2026-11-27、chico の判断で移した）。
- Workers の無料枠で足りる（1日10万リクエスト）。クラウドで動く Claude からも、コネクタとして登録すれば使える。

- Issue ごとにスレッドがあれば、その件の相談・進み具合・PR・レビューが1本で追え、AI もそのスレッドを読めば経緯が分かる。メンションしないので、スレッドが増えても通知はうるさくならない。
- スレッドを立てる時機は「Issue ができたら自動で」にした（AI が着手したときに立てる案もあった）。人が作った Issue にも必ず相談の場所ができるため。Actions のシークレットの登録だけリポジトリ管理者に頼む。

## 検討したほかの案

- GitHub 連動（PR でレビューを頼むと GitHub Actions が Discord に投稿し、返信を定期的に PR のコメントに写す）：エージェントごとの設定が要らず、やりとりが PR に残る。ただし返信が写るまで15〜30分かかり、AI がスレッドに直接答えられない。chico の判断で MCP サーバーを選んだ。
- 各自が手元で起動する（stdio、`.env` を配る）：ホスティングが要らないが、トークンを全員に配ることになり、クラウドのエージェントごとに環境変数とネットワークの許可も要る。最初はこれで始めて、上の理由で移した。

## 影響（変わること・注意すること）

- Worker は chico の Cloudflare アカウントにある。コードが `main` に入ると Actions が自動でデプロイする（2026-11-28、#37。それまではダッシュボードに貼る手作業だった）。
- URL の鍵（`ACCESS_KEY`）が漏れたら、Worker の設定で変えて URL を配り直す。トークンが漏れたら Developer Portal で「Reset Token」して Worker の設定を変える。
- メンバーが増えたら Worker の `DISCORD_MEMBERS` に足す。
- 通知が多いと無視されるので、気軽に呼ばない。小さな質問は PR・Issue のコメントで聞く。
