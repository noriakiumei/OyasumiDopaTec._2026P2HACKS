# 007: ルール・docs の変更は Issue なしで PR を出し、相談は「要相談」の Issue か PR に書く

- 日付：2026-11-26
- 決めた人：（PR のレビューで決める。#12 の案1。提案はいうてぃー）
- 変更：2026-11-26 公開したくない相談はドライブに書く、を足した

## 決めたこと

- `AGENTS.md`・`docs/`・`.github/` だけを変えるときは、Issue なしで PR を出してよい。
- AI や人の動きが変わる変更は、PR に「要相談」ラベルを付け、本文に背景・選択肢・おすすめ・返事がほしい期限を書く。
- 先に Issue を作るのは、差分で見せられない相談（リポジトリの設定、方針そのものなど）だけ。「要相談」の Issue テンプレートを使う。
- 相談の中身は「要相談」の Issue か PR に書く。ドライブの「03_判断・議事録」は、長い話し合いや議事録に使う。
- リポジトリは公開なので、個人情報・お金・チームの外に見せたくない相談は、中身をドライブに書き、Issue・PR にはリンクと期限だけを書く。
- AI は `gh pr merge`・自動マージの予約・ツールのマージ機能を使わない。

## 理由

- Issue の役割は、まだ始まっていない仕事を並べて、順番と担当を決めること。ルールや docs の変更は、思いついた人がそのまま PR を出せば、提案・差分・相談が1か所にそろう。
- PR はマージ前に全員が見られる。先に Issue を作ると、同じ相談を Issue と PR で2回することになる。
- 相談の中身をドライブに、リンクを Issue に、と分けると2か所を見ることになる。Issue と PR はどの AI からも読み書きできる。
- 「マージは人が行う」は前からのルール。道具の名前まで書いて、AI が迷わないようにした。

## 検討したほかの案

- 内容で分ける（文言の修正は Issue なし、意味の変更は先に「要相談」Issue）：線引きがあいまいで、AI がどちらか迷う。
- ルール・docs の変更にも必ず Issue を作る：手続きが増える。

## 影響（変わること・注意すること）

- 「要相談」テンプレートが New issue の画面に出ることと、ラベルが自動で付くことは、マージ後に画面で確かめる。
